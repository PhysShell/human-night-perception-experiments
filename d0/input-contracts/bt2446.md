## Implementation findings

- **libplacebo `bt2446a`** is the most trustworthy implementation found. The code was checked against Report Table 2:
  - It computes rho_HDR = 1 + 32(L_HDR/10000)^(1/2.4) and applies Y'p = log(1 + (rho-1) x^(1/2.4)) / log rho.
  - It uses the three-segment knee 1.0770 / (-1.1510, 2.7811, -0.6302) / 0.5, the inverse rho_SDR, and then BT.1886. All of this **matches Table 2**.
  - But it is only the Method A **luminance tone curve**, used as a 1D LUT inside libplacebo's own colour pipeline. It does not include the Table 3 colour correction (Cb/Cr scaling f(Y'SDR) = Y'SDR/(1.1 Y') and Y'TMO = Y'SDR - max(0.1 Cr, 0)). It also treats L_HDR as a parameter (`input_max`), where the report fixes 1000 cd/m^2.
  - It runs through libplacebo's GPU/Vulkan renderer or an FFmpeg `libplacebo` filter. Neither is in this nix environment, and a CPU-only path would need a C harness around libplacebo's colour pipeline. So it is not a runnable "BT.2446 Method A" here without porting, and it would still be partial.
- **HDRTools (jpsdr)** implements A and C, but as an AviSynth+ C++ plugin (Windows-centred build). Running it would mean building AviSynth+ and the plugin on Linux and feeding video frames. That is significant porting.
- **Method B:** no dedicated open implementation was found.
- No implementation of all three methods with clear provenance was found. As instructed, none of the methods was reimplemented.

## What each method expects (input semantics)

All three are **display-referred HDR to display-referred SDR** conversions of BT.2100 content (Rec.2020 primaries, PQ or HLG):

- **Method A (§4.1).**
  - Input: normalised full-range linear **display-light** BT.2100 RGB, assumed mastered at **L_HDR = 1000 cd/m^2**.
  - Processing: R'G'B' = RGB^(1/2.4); luma with the BT.2020 weights (0.2627, 0.6780, 0.0593); a perceptual-log knee (Table 2); then colour correction in Y'Cb'Cr' (Table 3).
  - Output: SDR Y'Cb'Cr' for **L_SDR = 100 cd/m^2**, BT.2020 container (convert to BT.709 via Report BT.2407 if needed).
- **Method B (§5.2).**
  - Input: **HLG** (PQ must first be converted to HLG per BT.2408 §6). HLG display EOTF with L_W = 291 cd/m^2 and system gamma 1.03, so HDR Reference White (75 % HLG) lands at 78 cd/m^2.
  - Processing: Yu'v'; a 1:1 luminance mapping up to the breakpoint (~55 cd/m^2, 78 % SDR) and an example log highlight compression above it (Fig. 6); hard clip to the BT.709 colour volume.
  - Output: RGB through the inverse BT.1886 EOTF (100 cd/m^2).
- **Method C (§6.1).**
  - Input: **HLG** display light (EOTF with system gamma 1.2); "similar conversion might be possible for PQ".
  - Processing: crosstalk matrix alpha in [0, 0.33]; Yxy; Y_SDR = k1·Y below Y_ip = 58.5/k1, log above it; k1..k4 = 0.83802, 15.09968, 0.74204, 78.99439 for HDR 1000 / SDR 100 cd/m^2 (Eq. 10); inverse crosstalk; optional achromatic highlights.

## Semantic gap for this project

Our scenes are **scene-referred** absolute luminance. S0 is a dark rural night with a median of 7e-5 cd/m^2, a 99.9th percentile of 0.013 cd/m^2 and a maximum of 0.48 cd/m^2.

- BT.2446 has no scene-to-display step. It assumes an already **graded HDR display rendering** in which "HDR Reference White" sits at 203 cd/m^2 (PQ 58 %) or 75 % HLG, and it maps that to about 86-96 % SDR.
- Applying it here needs a **prior HDR display rendering** (for example another donor's HDR1000 PQ output) encoded as PQ/HLG BT.2100. The BT.2446 output would then describe that renderer followed by BT.2446, not BT.2446 acting on the scene.
- If the absolute scene values were passed straight in as "display light" (cd/m^2 = nits), almost the whole night scene would sit in the linear/low segment:
  - Method C: Y_SDR = 0.838·Y, so night pixels stay at sub-0.1 cd/m^2 on the SDR display and fall below the 0.1 cd/m^2 SDR100 black.
  - Method A: a near-linear low segment.
  - That would be a misuse of the method, not its intended behaviour.
- BT.2446 has no viewer-adaptation, surround or viewing-geometry input: no px/deg, and no ambient term other than BT.1886/HLG conventions.

## Nothing was run

No outputs, and no `runs.json`. If a later stage has an HDR1000 PQ rendering of the scenes, libplacebo `bt2446a` (tone curve only, and not the Table 3 colour correction) is the candidate to evaluate first. It should be labelled as a partial Method A.
